# DanLM、FableDan、DouZero 架构审计与单 TPU 迁移决策

检索日期：2026-09-27。以下将“公开源码可确认的实现”“作者公开声明”和“本交付的设计选择”分开。本文不是三个项目的性能复现实验。文件路径均指来源仓库对应文件；运行手册另见 README.md。

## 一、三个项目并非同一规则体系下可以直接相加的模块

DouZero 是三人斗地主的 DMC 自博弈系统。DanLM 从掼蛋切入，用公开牌局历史的因果预测改善价值学习；其 README 在 2026-05-01 已公告斗地主版本 DouLM。FableDan 的已审计训练实现是四人掼蛋版本，公开了更完整的 PyTorch 训练、CPU ring、集中推理、辅助目标和 NumPy 导出代码。

DanLM 的公开 README 与评测入口支持核实“TinyLM + hand/action MLP + candidate Q + DMC/NTP”这条主线，但不足以让我核实完整训练源码及全部超参数。不能把 FableDan 的层数、批量和优化器反过来当作 DanLM 的准确配置。项目作者的排行榜/胜率描述，也不能直接作为不同规则、不同对手和不同计算预算下的可比证据。[1][2][3]

结论不是融合三个权重，而是采用：**DouZero 的规则与价值学习问题定义；DanLM 的历史表示思想；FableDan 的公开工程经验；为单芯片重新安排计算。**

## 二、DouZero：合法动作条件化的 Monte Carlo 价值回归

### 2.1 数据与网络

原始实现分别维护地主、上家农民、下家农民三套模型和优化器。每个候选动作编码为 54 维牌点数量二值矩阵；状态中包括自家牌、公开出牌、余牌数、上一动作等信息。历史最近 15 个动作按每三个一组组织成 `[5,162]`，经过输入 162、隐藏 128 的 LSTM。地主含动作特征为 373 维，农民为 484 维；加上 LSTM 的 128 维表示，经过五层 512 维 ReLU 隐层，最后输出一个标量。不是固定全集分类器，而是遍历当下合法动作集合求最大 Q。[3][4]

公开环境内部 infoset 确实可以访问各家真实手牌，但 policy 的可观察编码与完整模拟器状态必须区分。原版使用的“另外两家手牌并集”可由整副牌减去自家与所有已出牌计算，不等于把每张未知牌属于谁告诉模型。[4]

### 2.2 学习算法

一局终局后，把对应团队的最终回报赋给该角色在整局中每一次决策，优化 `(Q(s,a)-G)^2`。原始 CPU/GPU actor 通过分角色共享缓冲和队列发送样本，learner 更新后把权重同步给 actor；优化器为分角色 RMSprop。[5][6]

这不是 DQN：没有 `r+gamma*max Q_target(s',a')` 的默认 bootstrap 目标，也不需要目标网络。动态合法动作集合只影响推理时需要评估多少候选，不迫使价值头为整个动作全集预留固定输出维度。

优势是目标简单，适合终局胜负和动态动作空间；不足是信用分配粗、方差较大，并且仅用最近历史的 LSTM 不容易保留很早的让牌或出牌信息。公开累计统计保留部分长期信息，但不等于保存完整事件语义。

## 三、DanLM：改善表示，不是用语言模型直接生成出牌

公开设计将“谁在什么时候出了什么”转成 token 序列，由小型因果模型得到历史表示；手牌/候选动作仍走数值分支，再输出 Q。自博弈 DMC 提供稀疏结果监督，NTP 为序列表示提供稠密辅助监督。[1]

其价值在于可能从完整历史学出记牌、让牌、剩余结构与行为倾向，而非依赖大量人工设计的统计项。但“能预测下一个 token”不自动意味着学到了完整可规划的世界模型：行为策略会随训练改变，隐藏手牌产生不可消除的不确定性，NTP 也可能主要学到容易的格式和高频牌型。必须通过关闭 NTP 的等预算消融检验策略收益。

迁移到单 TPU 时，保留小词表和因果历史编码，不使用大型通用文本模型，不让自回归文本输出绕过合法动作过滤。领域知识仍存在于规则引擎、编码和目标定义中，更准确的表述是减少人工策略特征，而非字面上的绝对“零知识”。

## 四、FableDan：最值得借鉴的是可执行工程结构

### 4.1 网络与辅助任务

已审计 `model_torch.py` 默认 `d_model=128`、4 个 block、4 个注意力头、每头 Q/K/V 64 维、FFN 512。这里 4×64=256，是投影后的宽度，不能误读为常见的 128/4=32 每头。组件含 RMSNorm、RoPE、QK-Norm、SwiGLU 和因果 SDPA；hand/action MLP 隐藏宽度 512，Q MLP 隐藏宽度 1024，二者都较大。[7]

历史上下文先编码一次，再对每个候选重复使用，而不是为每个候选重新跑 Transformer。辅助目标包括 NTP 和另三家手牌计数预测；belief 由历史上下文产生，训练使用模拟器真值标签，部署导出移除两个辅助头。[7][8]

这类辅助真值训练并不等于推理作弊，前提是隐藏牌只进入 loss label，而没有进入实际动作选择输入。对于三人斗地主，维度应改成两家×15，不能照搬掼蛋三家×15。还可以让 belief 的输入合法地包括自家手牌，缩小隐藏信息的不确定性；本版采用这一变化。

### 4.2 训练调度

`fabledan/train_fast.py` 是面向双 GPU 的结构：多个 CPU actor，每个运行一组 ring 牌局；独立推理服务汇集请求；主进程用另一 GPU 学习。默认回放 262,144、每周期新增预算为 buffer/diversity=131,072、16 次更新、batch 4096、micro-batch 1024、Adam 学习率 1e-4。推理过程按实际最大序列长度和实际动作总数构建动态张量。epsilon=0.02 时在当前 Q 排名前 10 的动作中探索。[9]

这里“top-k 探索”不是“只计算 top-k 合法动作”：先得到全部候选的 Q 才能得到 top-k。在新模型早期，排位不可靠，所以本交付改用更高的均匀全合法动作探索，并逐步衰减。

FableDan 已有周期性快照、规则对手和冻结自快照评测、定时停止以及部署打包。但保存网络/优化器不等于保存完整回放、随机状态和所有在途牌局，也不等于面向临时 Colab 虚拟机的远端事务式保存。[9]

### 4.3 必须纠正的文档读法

`encode.py` 实际定义 `FEAT_DIM=80`，包括余牌数、完成标志、等级、动作类型、主动作类型、比较 key 等；一个函数注释仍写 69 维。因此不能只引用“feature-free”宣传而无视代码。它减少的主要是复杂策略特征，并非所有人工编码。[10]

`DESIGN.md` 将 belief、增强编码器、冻结快照评测标为已实现；TD-λ、对手池、一步搜索等是待实现方向，不能算进现成训练器。并且 `beta*MC+(1-beta)*one_step_bootstrap` 本身并不自动等价于严格的 TD-λ 回报；后者通常涉及多步回报的几何加权或相应递推。[11]

## 五、TPU v5e-1 改变了优化问题

Google 的规格是每个 v5e 芯片一个 TensorCore、16GB HBM、BF16 峰值 197TFLOPs；v5e-1 不能按旧的“八设备 Colab TPU”范式配置。整个八芯片 host 的 DRAM 表项，也不能作为 Colab 进程可用主机内存保证。[12]

将 PyTorch 的设备字符串替换为 XLA 并不能自动带来性能：Python 规则枚举仍在 CPU；可变合法动作数、可变历史和小批量设备往返会限制吞吐。JAX JIT 会按形状等签名编译；无限多的动态形状会造成编译和缓存压力。基准测试也必须等待设备完成，而不能只测异步提交时间。[13]

因此本版不追求一开始把整套规则向量化到 TPU，而是分成：CPU 负责正确规则和完整局回报；一个 JAX 进程负责批量编码/候选评分/梯度更新。它降低首版实现风险，但仍可能被 CPU 环境和主机往返限制，不能用芯片峰值反推每小时牌局数。

## 六、本交付的结构与预算

```text
CPU workers × ring games
  │ 公开历史、自家牌、余牌数、角色、全部合法动作
  ▼
单 JAX/TPU 主进程
  ├─ 历史编码一次：3-layer, d128, 2×64 heads
  ├─ 融合 21 维合法状态
  ├─ 16 维候选动作分块评分：2048/块，无截断
  └─ 返回动作下标
  │
CPU 收集完整局 → 回报附到每条决策 → 紧凑回放
  │
TPU：DMC MSE + 0.02 NTP + 0.05 belief
  │
本地验证快照 → Drive 世代归档与提交标记
```

### 6.1 表示与网络

共享一个 922,401 参数的骨干，末端使用三个角色标量头。斗地主角色不对称，因此保留身份信息和角色头；共享历史和动作表示节约重复计算。此选择未被证明优于三独立网络，后续应比较共享、分头和分模型三种配置。

序列的保守上界是 486，因此使用 512 并拒绝静默截断。自家手牌进入当前状态分支，不广播给过去 token 的 NTP 分支。这样辅助任务不会利用当前手牌中的后验信息去“预测”已经发生的过去。

默认基干矩阵 BF16，参数/优化器/最终 Q 投影/损失 FP32；注意力 softmax 用 FP32，重计算控制激活内存。学习 micro=32、accumulation=8、等效 batch=256；只在单设备上使用 JIT 和 scan，不伪装成八芯片数据并行。

### 6.2 动态动作问题

状态批次 64；推理历史仅四个长度桶。编码后的状态按 owner 索引供扁平化候选动作引用。候选不足块长就 padding 并标记无效，多于块长继续下一块。测试包括 4101 个候选跨越默认 2048 动作块，以及多个状态/角色的索引一致性。

该分解把历史编码从“每个候选一次”变成“每个状态一次”。过大的 action MLP 仍然会随着候选数线性放大，因此本版不用原 FableDan 1024 宽度的深候选 Q 网络。

### 6.3 样本与目标

回放 65,536 条约 41.375MiB 纯 NumPy 存储；实际主机用量还含模拟器、在途轨迹、消息序列化、JAX 和缓存。按角色平衡采样；周期年龄上限 64；每周期至少新增 2048 条完整局样本、4 次更新，名义使用/新增比 0.5。默认不扩大模型，也不通过过度复用少量数据“制造”很高的 TPU 利用率。

终局目标为团队 WP ±1。农民队友获胜也是本方胜。Q MSE、每序列归一化 NTP 和两家手牌计数 MSE 联合优化；这些权重是起点，不是经过 TPU 消融证明的最优值。

本版采样与学习阶段交替，不完全异步。跨周期未结束的牌局可能经历不同策略版本，回放也不是严格 on-policy。限制年龄和更新强度只能控制滞后，不能声称 MC 数据对最新策略严格无偏。

## 七、Colab 自动化的真实边界

Notebook 已内嵌所有本项目源码；安装修复只在依赖缺失、失效或未发现 TPU 时尝试一次。优先沿用可用 JAX/TPU 栈，必要时使用官方 `jax[tpu]` 安装路线，不同时引入 torch_xla。Notebook 内核不初始化 TPU，以免和训练子进程争用。[14]

首次运行需要选对运行时并授权 Drive。之后代码完成来源锁定、CPU 自测、TPU 形状预检、训练/恢复、评测、保存和导出。Colab 的运行时资源、空闲与最大生命周期并非永久保证；代码不能自动代替用户授权或申请新虚拟机，也不应使用保活脚本绕过限制。[15]

快照采用只认提交标记的世代归档：本地写好、逐文件和整包 SHA 校验、复制远端、最后提交，保留三代。初始持久化失败会阻止长训练启动。Drive 后续故障明确告警，最后同步不成功则以错误结束。每 300 秒是安全点检查间隔，长编译和远端 I/O 会延迟。

恢复涵盖模型、AdamW、回放、主 RNG 和计数器，不涵盖在途局的完整状态。更换虚拟机需要重新运行 Notebook，也可能重新编译；这不是无人介入、无限期运行服务。

## 八、评测与下一步研究顺序

内部评测把同一份牌打两次，交换当前/对手的地主与农民团队身份，按牌局对做 bootstrap；同时输出两个身份的胜率和均值。默认 32 对只是工程监控。冻结冠军的选择也会受固定牌集影响，不能把 `best_policy.npz` 这个名字当作外部最强证明。

可信的实验应区分独立验证牌集、未参与模型选择的最终测试牌集，并记录双方权重版本、目标规则、角色分配、epsilon=0 的评测策略以及计算预算。至少比较：DMC；DMC+NTP；DMC+NTP+belief；共享/独立角色骨干；均匀/局部 top-k 探索。用相同实际训练时间或相同完整局样本数分别作比较，避免吞吐和样本效率混淆。

针对官方 DouZero 权重的可选 CPU 对手接口已经提供，要求三份可信 state_dict 并记录哈希。本次没有官方权重，因此尚未完成真实权重端到端验证；没有任何本版战胜它的实验结论。

先验证规则和信息边界，再测端到端瓶颈，然后通过消融调辅助权重，最后才考虑异步重叠、KV 缓存、C++/JAX 规则、联盟、TD-λ 或搜索。相比把更多先进术语叠加进首版，优先得到可以恢复、可以复现对局条件、可以定位瓶颈的基线更有价值。

## 九、实际验证记录

在本地 CPU（Python 3.13.5、JAX 0.9.0.1、NumPy 2.3.5）上：9 项单元测试通过；参考引擎 200 局、9188 个行动步的自测通过；微型网络完成两周期训练及配对评测；从另一工作目录读取持久化目录后恢复并更新至第三周期；BF16、四种历史形状、合成梯度预检通过；部署裁剪后权重重新载入并完成参考引擎对局。

其中持久化测试使用普通本地目录模拟远端，不是实际 Drive；参考引擎不是已验证的官方规则替身；小模型时间和微量胜率不能外推生产强度。真实 Colab/TPU、上游下载与 Drive 挂载、官方预训练对手仍需 Notebook 运行时验收。完整日志随源码附带。
